## Backlog refinement

### Intended outcome

Permanently clear unwanted screenshots from Trash, including clearing the whole Trash in one action, and reclaim their local image/preview storage.

### Evidence and current behavior

The attached screenshot shows four selected items in Trash with Restore selected available and no permanent-delete action. Current trashImage only records trashedAt/trashedBy; it retains the base image, preview, annotations and links indefinitely.

### Proposed scope

Add Delete permanently for selected trashed screenshots and an Empty Trash action. Use an explicit confirmation preview with an exact count and image list. Preserve useful ticket/conversation references and annotation instructions through a small deletion record or equivalent placeholder; do not silently rewrite unrelated Markdown or delete linked tickets.

### Acceptance criteria

- [ ] Trash offers Delete permanently for selected items and Empty Trash for all currently trashed items; the normal screenshot library continues to use reversible Move to Trash behavior.
- [ ] Confirmation names the exact images/count and explains that local image/preview files will be removed. Empty Trash clearly covers the entire Trash, even when a search filter is active; selection deletion covers only its explicit selection.
- [ ] Cancellation makes no changes. Confirmation freezes the candidate list and revisions; newly trashed images are not swept into an already-open confirmation.
- [ ] Only currently trashed images are eligible. An image restored or edited after the preview is rejected individually rather than being deleted with a stale revision.
- [ ] Successful deletion removes base/preview assets and removes the entry from the ordinary Trash list. Empty and repeated-delete states are handled consistently.
- [ ] Linked tickets and conversation prose remain intact. Their screenshot references clearly indicate permanent deletion, with retained written annotation context where available; a missing or purged image never crashes board/detail/context rendering.
- [ ] Partial failures identify confirmed deletions and remaining items without replaying uncertain destructive requests automatically. Controls prevent duplicate submissions.
- [ ] Existing backups are not modified. Export/restore handles deletion records consistently, and a pre-deletion backup can restore the original image and links through the existing restore workflow.
- [ ] Keyboard focus, confirmation defaults, narrow layouts and both density modes work. Tests exercise cancellation, filtered selection, full-Trash scope, concurrent restore/edit, missing files, linked images and partial failures using disposable assets.
