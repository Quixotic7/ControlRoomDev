## Intended outcome

Let a designated reviewer/orchestrator agent coordinate workers through Control Room, independently review their submissions, accept satisfactory work into Done, and escalate work that needs human judgment or feedback. The human sees a clear account of who is doing what and why work was accepted or escalated.

## Requested workflow

1. Orchestrator decomposes permitted work into tickets, adds acceptance criteria/dependencies/context and assigns a named worker.
2. Worker acknowledges/claims the assignment, works in its checkout, reports progress or blockers, and submits a handoff plus verification evidence to Review.
3. Orchestrator inspects the implementation against the acceptance criteria, applicable decisions and UI rules. It checks the submitted code state and performs independent verification where appropriate.
4. Orchestrator records one of three outcomes: Accept into Done; Request changes with actionable feedback; Needs human with a specific question or review request.
5. Human responses return the ticket to the appropriate worker/reviewer queue without losing the prior review history. Humans can override/reopen outcomes.

## Proposed product rules

- Keep worker, orchestrator and human roles distinct. Agents remain attributed as agents and never impersonate a human to accept work. Human explicitly designates an orchestrator and can revoke its authority. The existing human-review workflow remains the default unless orchestration is enabled.
- Worker submissions do not self-approve. Record assignment, worker identity, reviewer identity, outcome, rationale, acceptance criteria checked, evidence and reviewed code state separately. Flag cases where the reviewer also performed implementation for independent/human review.
- Delegation uses durable assignments separate from expiring execution claims. Assigned does not mean acknowledged, claimed does not prove running, and expired claims do not silently free an active worker's checkout. Reassignment preserves history and handles late submissions explicitly.
- Review decisions take the ticket revision and the submitted code/evidence identity. Changed submissions require fresh review. A green test alone is not proof of the intended outcome. Missing or stale evidence must be resolved or escalated.
- Needs human is explicit routing of a question/review, not an ambiguous blocker string. Explain what the human must decide, show the relevant diff/screenshot/evidence, and preserve any unsent feedback. Human-required tickets cannot be quietly auto-accepted.
- Acceptance is separate from Git operations. Do not implicitly merge, push or deploy when accepting a ticket. Where the project defines integration as part of Done, verify the integrated result before acceptance.
- Parent completion remains a deliberate outcome review, not automatic completion when children close.
- Show the agent roster, assigned/claimed work, review queue, Needs human queue, review outcome badges and acceptance history in the UI. Keep authoritative records readable in Markdown.
- Expose matching CLI/MCP operations and role-specific context/protocols so different models and coding tools can participate.
- Identity labels are workflow attribution for agents sharing the local account; they are not a strong isolation/security boundary.

## Confirmed interview choices

- Control Room should launch and supervise coding agents itself. This is in scope for the first version, not merely assigning tickets to manually running agents.
- The orchestrator may start/decompose/reprioritize work only within human-approved goals or tickets. It cannot approve new scope for itself.

## Managed agent lifecycle requirements

Use an adapter per coding tool with structured run events/results where available. Record requested, launching, running, waiting for input, completed, failed, interrupted and unknown/recovery states separately from ticket status. Track run ID, assigned ticket, role/model, checkout/branch, process identity, last event and final result. A process exit does not complete a ticket; a review receipt does.

Allocate isolated worker worktrees, limit concurrent runs, honor ticket dependencies and surface overlapping work before integration. Persist recoverable run metadata locally; keep credentials out of board records and exports. After service restart, reconcile existing runs instead of blindly launching duplicates. Cancellation must stop the relevant run and leave its worktree/diff and handoff recoverable. Approval prompts, authentication failures, unavailable tools, usage limits and ambiguous exits should become explicit agent/Needs-human states. Add configurable retry/resource limits so blocked work does not spin indefinitely.

The orchestrator should run through the same adapter boundary, consume board events and resume with durable context. No API-provider credential or embedded model subscription is assumed; supported harness setup must be explicit. Worker results are claims to review, not trusted acceptance instructions.

## Implementation outline (proposal)

A. Role/policy configuration, review routing and durable review receipts; preserve existing human behavior and Markdown compatibility.
B. Assignment/acknowledgment/reassignment, worker queues, dependencies and worktree conflict visibility, CLI/MCP protocol.
C. Orchestrator review context and accept/changes/escalate operations, evidence/code identity checks, human-response continuation and parent review.
D. Human dashboard and history, plus a documented end-to-end trial with at least two workers.
E. Launch/supervision adapters and recovery are required in the first version, using the coding tools selected in the interview.

## Acceptance checks

- Two named workers can receive distinct assignments and cannot silently overwrite claims or review decisions.
- A worker cannot accept its own work or grant itself reviewer/scope authority through ordinary workflow operations.
- A designated orchestrator can accept a permitted current submission with an attributed review receipt, request changes, or escalate it with a specific question.
- Human-required work, changed evidence/code, revoked reviewer authority, stale revisions, expired claims, late submissions and retry exhaustion have explicit outcomes.
- Questions do not expire. Human answers, review history, assignments and acceptance receipts survive service restart and Markdown reload.
- The board distinguishes orchestrator-accepted from human-accepted work and exposes any unverified integration state.
- Existing projects retain their current human-only acceptance behavior until orchestration is explicitly enabled.
