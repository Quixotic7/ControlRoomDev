Requested by the JuiceLab coordinator (JuiceLab board #33, owner asked for Control Room tickets in chat, 2026-10-01).

## Problem

A managed run gets one Git worktree of one repository, created under the board:
`.controlroom/.local/orchestration/worktrees/<run>` (`src/orchestration.ts`, `perform`). JuiceLab cannot use that:

- Machine Lab's `Package.swift` depends on the sibling checkout `../juicebox` by path, and its pin check
  (`tools/check-juicebox-pin.py`) reads the same path. Under the board there is no sibling, so a managed worker
  cannot build or self-test Machine Lab at all.
- The JuiceLab board tracks two code repositories (Machine Lab and JUICEBOX). Only one `repository` can be
  configured, so JUICEBOX tickets, and tickets that change both, cannot be delegated.

## Wanted

- Companion repositories in the Agents configuration: for each, a repository root, a base ref, and the path it
  must have relative to the main worktree (for JuiceLab: `../juicebox`). A run gets a worktree of each, on its own
  `controlroom/<run>` branch, laid out so the relative paths hold (for example a per-run folder holding
  `juicemachinelab/` and `juicebox/`).
- A read-only companion option (a detached worktree at the base ref) for runs that only build against it.
- Review, code identity, changed files, the verification command and the acceptance receipt cover every
  repository of the run; the integration note names each branch.
- A ticket can say which repositories it touches (a field or label), so a Lab-only ticket does not create a
  writable JUICEBOX branch.

## Acceptance criteria

- With Machine Lab as the repository and JUICEBOX as a companion at `../juicebox`, a managed run can run
  `python3 tools/check-juicebox-pin.py` and `swift build --product MachineLab` in its worktree.
- A run that changes both repositories shows both diffs to the reviewer and records both branches.
- Existing single-repository boards behave as before.
