## Intended outcome

Open and use the same project board from another device on the local network while keeping the existing local browser, CLI, worktree coordination and capture service functional.

## Investigation

The current behavior is deliberate, not a missing firewall rule: src/cli.ts binds the service to 127.0.0.1, and src/server.ts rejects non-loopback Host headers. The current browser bootstrap also grants the project cookie to local page requests. Changing only the listener would still fail the Host check; removing both restrictions without replacing the bootstrap would grant project access to any reachable visitor.

## Proposed implementation scope

Add explicit, project-specific LAN access while retaining local-only operation as the default. Show the usable address and connection instructions in the application. Require pairing by default, with a host setting to allow direct trusted-LAN access without a code and a configurable paired-access duration. Never issue the local project credential to remote page requests. Keep local agent discovery pointed at loopback. This ticket concerns the existing single-user board on a trusted local network, not a hosted service or multi-user permission system.

## Acceptance criteria

- [ ] An explicit LAN option exposes the board on the intended local interface and reports usable addresses/port; existing loopback launchers and CLIs continue working.
- [ ] Local-only remains the default. The application reports which mode is active, and disabling LAN prevents further remote access without deleting records.
- [ ] A second device can authenticate and use tickets, comments, screenshots and live updates. When pairing is required, unauthenticated visitors cannot read project records, images, event streams or backups, or perform mutations. When the host explicitly disables pairing, trusted-LAN visitors can use the board directly; host-only controls remain protected.
- [ ] Remote credentials are not embedded in page HTML, asset URLs, logs or ordinary share links. Pairing/session expiration and revocation have a clear recovery path.
- [ ] Host/origin checks remain explicit and project sessions remain isolated across projects/ports. Cross-origin requests and arbitrary Host headers remain rejected.
- [ ] The chosen transport and its limitations are documented accurately; remote connection setup must not imply encryption that is absent. No router port forwarding or public exposure is configured automatically.
- [ ] Local-machine controls such as native capture, shutdown and filesystem import/restore receive an explicit remote-access policy instead of becoming accidentally available through a listener change.
- [ ] Existing running-service discovery, restarts and project-specific launchers honor the selected mode. Address changes, unavailable interfaces and firewall failures produce actionable connection guidance.
- [ ] Automated tests cover local-only behavior, authenticated/unauthenticated LAN requests, origin/Host rejection, credential isolation and revocation. Verify a real second-device browser connection separately from same-machine HTTP tests.
