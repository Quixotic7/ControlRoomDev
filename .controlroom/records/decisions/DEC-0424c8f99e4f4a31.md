## Choice

Retain local-only startup and require pairing by default when LAN access is enabled. The host can turn off Require pairing code in Network access settings. In that explicit mode, devices on the permitted trusted LAN can read and edit the project without a code. Host-only controls and Host/origin checks remain enforced, and local tokens are never issued to remote visitors.

Let the host set paired access duration in hours, from 0.25 (15 minutes) to 8760 (365 days), default 8. The value applies to new pairings; existing sessions retain their original expiry unless revoked. The one-use setup code still expires after ten minutes. Keep authentication preferences in ignored project-local state across restarts and CLI mode changes.

Changing whether a code is required clears existing paired sessions and outstanding codes. Turning the requirement back on immediately closes unauthenticated event streams and requires fresh pairing. Open access lasts while LAN is enabled with pairing disabled; it does not use a per-browser access timer. Disable LAN to stop all remote access.

## Context and rationale

The human confirmed a successful connection from another device, but requested optional codes and configurable access duration in the September 27 review of #63. The previous mandatory pairing/eight-hour policy imposed unnecessary friction for this trusted-LAN use case.

## Alternatives and tradeoffs

Mandatory pairing is still the default. Open mode deliberately permits project-wide access to reachable trusted-LAN devices; Settings makes that consequence explicit beside the option. HTTP remains unencrypted. There is no public hosting, automatic firewall change, or separate user permission model. Duration changes apply prospectively to avoid unexpectedly changing already-granted sessions; Revoke all remote sessions resets existing grants immediately.
